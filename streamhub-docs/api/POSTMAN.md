# OpenAPI spec & Postman

The core exposes the full REST surface as an OpenAPI (Swagger) document. This page explains how
to get the spec, import it into Postman, and wire up bearer auth against a running StreamHub.

- **Committed snapshot:** [`openapi.json`](./openapi.json) in this folder — a snapshot of the Go
  core's `/api/v1/openapi.json`. Import this directly if you don't have a live server handy.
- **Live endpoints (on any running core):**
  - Swagger UI: `GET /api/v1/docs`
  - OpenAPI JSON: `GET /api/v1/openapi.json`

Every route in the spec lives under the `/api/v1` prefix except `/metrics` and the static mounts
(`/hls`, `/samples`, `/sdk`, `/play`, `/embed`, `/assets`). See
[README.md](./README.md) for the human-readable endpoint reference with permissions.

## Getting the spec

### Option A — use the committed snapshot (no server needed)

Just use [`streamhub-docs/api/openapi.json`](./openapi.json). It is the contract snapshot the
2.x core exported (the Go core keeps every route and `operationId`). To refresh it from the Go
core, boot one locally with no infra and save its live document:

```bash
cd streamhub-core-go
go build -o bin/streamhub ./cmd/streamhub
DATA_DIR=$(mktemp -d) STREAMHUB_SHADOW=1 PORT=3999 ./bin/streamhub &   # no Redis/LiveKit needed
curl -fsS http://127.0.0.1:3999/api/v1/openapi.json | jq . > ../streamhub-docs/api/openapi.json
kill %1
```

The spec is generated by huma from the registered Go routes, so the binary needs **no Redis,
no LiveKit, no network** to serve it; `STREAMHUB_SHADOW=1` skips the background starters and a
throwaway `DATA_DIR` keeps it off real data. Re-run it after adding or changing endpoints and
commit the updated `openapi.json`.

### Option B — pull it from a running server (runtime export)

If you have a live core (locally or on a node), fetch the document straight from the running
service. The endpoint is public (no auth needed just to read the schema):

```bash
# local dev core
curl -fsSL http://127.0.0.1:3020/api/v1/openapi.json > openapi.json

# through a deployed origin's reverse proxy
curl -fsSL https://media.example.com/api/v1/openapi.json > openapi.json
```

The core also writes an `openapi.json` into its working directory on every boot (best-effort),
so the file is available on the server without curl.

## Import into Postman

1. **Postman → Import** (top-left) → drag in `openapi.json` (or paste the
   `…/api/v1/openapi.json` URL).
2. Choose **OpenAPI 3.0** when prompted → **Import**. Postman generates a collection named
   **"StreamHub core API"** with a folder/request per endpoint, including path/query params and
   example bodies from the DTOs.
3. Postman also creates an **environment** with a `baseUrl` variable (see below).

> Tip: on import, set "Request parameter generation" to *Schema* so bodies are prefilled from the
> DTO schema.

---

## Configure the base URL

The spec's paths are prefixed with `/api/v1`, so `baseUrl` must be the **origin without the
prefix** — Postman appends the path from each request.

| Deployment | `baseUrl` |
|---|---|
| Local dev core | `http://127.0.0.1:3020` |
| Deployed origin (TLS) | `https://media.example.com` |
| Deployed origin (bare IP / `--no-tls`) | `http://<origin-public-ip>` |

Set it in **Environments → your env → `baseUrl`**, and select that environment (top-right) so
`{{baseUrl}}` resolves in every request.

## Bearer auth with an `sk_` token

The REST API authenticates with `Authorization: Bearer <credential>` — an `sk_…` API token
(global or per-app, seeded by `streamhub-core seed-token`) or a login JWT. For scripting, use an `sk_`
token.

1. Get a token: copy the `sk_…` printed in the installer summary, or seed one with
   `printf '%s' "<value>" | docker compose exec -T core streamhub-core seed-token -`.
2. In Postman, set it **once** at the collection level so every request inherits it:
   **Collection → … → Edit → Authorization → Type: Bearer Token**, and set **Token** to
   `{{apiToken}}`.
3. Add `apiToken` to your environment with the `sk_…` value (mark it **secret** so it's masked).
4. Requests default to **Inherit auth from parent** → they all send the bearer header. Endpoints
   marked *public* in [README.md](./README.md) (e.g. `/auth/login`, `/health`) work without it.

The `addBearerAuth()` in the spec surfaces this as a **"bearer"** security scheme, so Postman's
generated collection already has the Authorization tab wired for you — you only supply the token.

## The `{data, error}` envelope

Most endpoints wrap their payload in an envelope, so read the body accordingly:

```jsonc
// success
{ "data": { /* the actual resource/list */ }, "error": null }

// paginated list variant
{ "data": [ /* rows */ ], "total": 128, "limit": 50, "offset": 0 }
```

- On **success**, the resource is under `data`; `error` is `null`.
- On **failure**, you get the proper **HTTP status** (4xx/5xx) plus a `{statusCode, message, error}` body — do not
  expect a `200` with `error` populated. Check the status code first.
- A handy Postman **test script** to unwrap it:

  ```js
  const body = pm.response.json();
  pm.test("status 2xx", () => pm.expect(pm.response.code).to.be.within(200, 299));
  pm.test("no error", () => pm.expect(body.error ?? null).to.be.null);
  // pm.environment.set("lastId", body.data?.id);  // chain into the next request
  ```

Note: the OpenAPI **response schemas** describe the inner payload shape; the `{data, error}`
wrapper is applied by a global interceptor and is the same on every wrapped route.
